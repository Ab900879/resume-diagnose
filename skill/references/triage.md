# 三分类判据

分类错了，后面全错。一个 C 类被判成 A 类，用户会拿着被润色过的简历去投一个根本投不进的岗。

## 先定「核心要求」

从 JD 里只取**硬要求**，3–5 条。判断标准：

- 是"必须会"的能力项（不是"有热情""抗压"这类软描述）
- 去掉重复表述和套话
- 一条要求只写一句人话

举例，原始 JD：

> 1. 能独立撰写 PRD，含边界条件与验收标准
> 2. 能把需求落成原型或流程图（Figma / Axure）
> 3. 对 LLM 能力边界有认知，自己搭过 AI 应用
> 4. 能定义评测标准、跑评测、做 badcase 归因
> 5. 能跨职能协作，推动研发与算法落地

五条都是硬要求，保留。如果 JD 里出现"有责任心""学习能力强"，直接丢掉，不占配额。

## 三条判据

对每条核心要求，给事实库里的经历评一个强度：

| 强度 | 判据 |
|---|---|
| 强 | 有直接证据，且 `verifiable` 为高或中 |
| 中 | 有可迁移的间接证据，或 `verifiable` 为低 |
| 弱 | 只有名词，没有动作（如技能栏写了但项目里没出现） |
| 无 | 全篇找不到任何相关痕迹 |

然后按下面归类：

### A 措辞型

- 「无」为 0 条，且「强」≥ 3 条
- 特征：能力都在，问题是没写清、没写数字、顺序不对
- 输出：完整四段 + 逐句改写

### B 重构型

- 「无」≤ 1 条，但「弱」≥ 2 条
- 特征：经历过，但写成了执行者视角。「配合」「协助」占全文动词的一半以上
- 输出：**先追问，不直接改**

B 类的坑：模型看到「配合完成 20 场活动」会自动改成「主导 20 场活动」。它不认为这是编造，它认为这是表达优化。所以必须逼出用户自己的判断作原料：

> 这 20 场里，有没有哪一场是你自己定的方案？当时还有别的做法吗，为什么没选它？

问到原料才改。问不到就说「这条按现在的事实改不了，除非你能想起一个具体的决定」。

### C 资格型

- 「无」≥ 2 条
- 特征：不是没写清，是真没有
- 输出：三段，且**明确说不建议投**

C 类最容易被误判成 A 类，因为简历上有相关名词（技能栏写了 SQL、写了 Figma）。**判据是项目里有没有对应的动作，不是技能栏有没有这个词。**

## 边界情况

| 情况 | 判法 |
|---|---|
| 「无」正好 2 条，但都是加分项（如"有 published 作品"） | 归 B。硬门槛没缺就还能救 |
| 「无」2 条，其中一条是 JD 点名的第一条 | 归 C。第一条硬要求缺失，后面写再好也过不了初筛 |
| 技能栏有的能力，项目里一次没用到 | 算「弱」不算「强」。技能栏是自我介绍，不是证据 |
| 用户说"这个我在学校学过" | 停在「弱」。学过不是做过 |
| 简历只有 1 页且信息量极少（≤5 条事实） | 不做分类，先让用户补经历 |

## 已验证的误判案例

以下是首轮实测中真实发生过的，用来校准：

1. **有 4 年工作经历 + 行业背景，看起来非常匹配，实际是 C 类。**
   JD 硬要求是 SQL（点名窗口函数）、建模语言、BI 工具。他四条里 0 条具备，只是行业经验强。
   → 教训：**匹配感来自行业，资格看硬技能。两者要分开算。**

2. **运营岗转投 AI 产品岗，有"离用户最近"的优势，被判 C 类。**
   JD 明确要"自己搭过 AI 应用、能写清楚一份 PRD"，他两条全无。
   → 教训：**可迁移优势不能抵硬门槛。C 类照样是 C 类，但可迁移项要写足，因为那是他真正能用的东西。**

3. **技术岗转产品，会写代码但没写过 PRD，被判 B 类。**
   → 教训：技术能力是强证据，但角色定位要重构。这类人最容易被改成"全栈产品"，反而四不像。

## 定位风险（累计 3 份真实案例后回看）

首轮 5 份虚构样本里，A 类只占 1 份（20%）。
如果真实求职者里也是这个比例，那这个产品的核心价值就不是"改简历"，是**"告诉你现在该投什么、该补什么"**。

**判定线**：累计 3 份真实案例后统计 C 类占比。
- C 类 > 50% → 产品定位从「简历优化助手」改成「投递决策助手」，主输出从改写变成投递策略
- C 类 < 30% → 维持现状，改写仍是主功能
- 30%–50% → 两类输出并列，首页要放两个入口

不要凭感觉改定位。等数据。
