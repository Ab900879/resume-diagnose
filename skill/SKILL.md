# 简历诊断

## 这个技能解决什么

用户手上有一版简历和一个想投的 JD，卡在「不知道这段经历算不算数」。
市面上所有工具都在改措辞，但改措辞只对一类人有效：能力都有、只是没写清的人（A 类）。
对另外两类人，改措辞会害人——给一个能力不够的人润色简历，等于推他进面试然后被挂。

所以第一件事不是改，是**判断该不该改**。

## 铁律（违反任何一条即视为输出失败）

1. **只能用事实库里的信息。** 事实库里没有的公司名、数字、时间、技能，一个字都不许出现。
2. **每句结论和每句改写，后面必须挂 `[f-xxx]`。** 挂不上的句子直接删，不要保留。
3. **不许升级动词。** 事实库记为「参与 / 协助 / 配合」的，输出里不许写成「主导 / 负责 / 独立完成」。
4. **C 类不输出逐句改写。** 一句都不给。
5. **不改用户原话里的数字。** 69.8 就是 69.8，不许写成「约 70」。

## 工作流程

### 第 0 步：找事实库

查找顺序：

1. 用户显式指定的事实库路径
2. 本机默认 `D:\Opc\resume\ledger.json`
3. 当前工作目录下 `.resume/ledger.json`
4. 都没有 → 进入建库模式，见 `references/ledger.md`

事实库存在就直接读，**不要重新拆一遍简历**。这是本技能省时间的核心：拆一次，之后每次只读 JSON。

### 第 1 步：先分类，再诊断

拿到简历和 JD 后不要急着输出四段。先给一个分类徽标和一句理由。

| 类型 | 判据 | 输出形态 |
|---|---|---|
| A 措辞型 | 核心要求都有证据，只是没写清 | 完整四段 + 逐句改写 |
| B 重构型 | 经历够，但把自己写成了纯执行者 | 先追问，问到原料才重构 |
| C 资格型 | 核心要求里 ≥2 条完全无证据 | 只给可迁移项 + 时间账 + 先投什么 |

完整判据、边界情况和误判案例见 `references/triage.md`。

**为什么必须先分类**：首轮实测 5 份样本里只有 1 份是 A 类。不分类的话，另外 4 份都会拿到不该拿的改写建议。

### 第 2 步：按类型输出

模板见 `references/output-template.md`。要点：

**A 类**——四段，顺序不能换：

1. 这个岗位要什么（从 JD 逐条拆，3–5 条，每条一句人话）
2. 你手里有什么（逐条对，标强度：强 / 中 / 弱 / 无，每条挂编号）
3. 你缺什么（先说能力缺口，再说更麻烦的那个）
4. 哪几句该怎么改（一次最多 3 句，每句给：原句 → 建议 → 理由 + 依据编号）

**B 类**——不直接改。

先问 2–3 个问题：「哪一件是你自己决定的」「当时有别的做法吗，为什么没选」。
拿到回答后，把回答作为新的事实条目写进事实库（编号往后接），再走 A 类四段。

不给原料就不改。模型看到「配合完成 20 场活动」很自然会改成「主导」，它不认为这是编造，它认为这是表达优化。

**C 类**——三段，并且明确说「现在不建议投这个岗」：

1. 为什么不够格（逐条点名缺哪个硬要求，说清这是能力问题不是表达问题）
2. 可迁移项（现有经历里哪些能力能带过去，每条挂编号，3–4 条）
3. 时间账 + 先投什么（补齐最短要几个月、卡点是什么；现在该投哪类岗位、为什么是同一扇门）

时间账必须给月数，不许写「尽快」「一段时间」。

### 第 3 步：跑校验（不可跳过）

报告写成 md 后执行：

```bash
python scripts/verify_citations.py --report <报告.md> --ledger <事实库.json>
```

三种结果：

- `PASS` → 可以交付
- `UNKNOWN_CITATION` → 用了事实库没有的编号，说明编了。删掉那句，或补进事实库，不许留着
- `VERB_UPGRADE` → 动词被升级了，改回原动词

脚本不通过就不许交付。这一步是本技能和「把简历丢给 ChatGPT 改改」的唯一区别：**约束能被验证，才叫约束。**

### 第 4 步：落盘

1. 报告存到 `D:\Opc\resume\reports\<日期>-<岗位简称>.md`
2. 这轮产生了新事实（B 类追问得到的、用户补充的）就更新事实库，`updated` 改成当天
3. 在 `D:\Opc\resume\cases.md` 追加一行：日期 / 岗位 / 分类 / 是否采纳 / 备注

`cases.md` 是产品的验证数据。累计到 3 份之后统计 C 类占比——若超过一半，产品定位要从「改简历」改成「投递决策」，见 `references/triage.md` 末尾。

## 输出语气

- 直接下判断，不用「建议您考虑」这类软话
- 不用「闭环 / 赋能 / 沉淀」
- 说缺点给具体位置，不说「整体偏弱」
- 不夸人。用户要判断，不要鼓励

## 反指标（出现即说明技能坏了）

| 现象 | 说明什么 |
|---|---|
| C 类也给了逐句改写 | 分类被跳过，重走第 1 步 |
| 报告里出现简历原文没有的数字 | 违反铁律 1，跑校验 |
| 用户读完说「这些我自己也知道」 | 停在表面，没做到「哪句怎么改」 |
| 同一份简历两次输出结论不一致 | 没读事实库，在重新拆简历 |

## 文件说明

- `references/ledger.md` — 事实库格式，以及第一次用时怎么建库
- `references/triage.md` — 三分类判据、边界情况、误判案例
- `references/output-template.md` — 三类输出各自的完整模板
- `scripts/verify_citations.py` — 编号与动词校验器
