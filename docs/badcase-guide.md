# Bad Case 分析指南

> 这个产品最值钱的部分不是"能生成报告"，是**知道自己会错在哪、错了怎么改**。
> 这份文档定义什么算 bad case、怎么判定严重度、记录成什么格式。

## 一、什么算 bad case

**判定标准只有一条：模型输出里，有任何一句会让用户照着做之后吃亏，就算。**

不是"输出不好看"，不是"我觉得可以更好"。是**用户照做会出问题**。

## 二、六类错误（按严重度排序）

| 级别 | 类型 | 含义 | 后果 |
|---|---|---|---|
| **P0** | 编造 | 输出了简历里没有的事实、数字、经历 | 用户在面试里被问倒，最严重 |
| **P0** | 资格误判为可投 | 明显不够格却判 A/B 类，还给改写 | 推人进面试被挂，且浪费投递机会 |
| **P1** | 动词升级 | 原文的"协助/参与"被写成"主导/负责" | 面试第一问就露 |
| **P1** | 分类错误 | 该 B 判成 A（跳过追问直接改），或该 A 判成 C（白劝退） | 建议不可用 |
| **P2** | 漏判 | 简历里明明有证据，报告说"无" | 用户被低估，不敢投 |
| **P2** | 溯源失败 | 结论挂了编号，但编号对应的事实对不上这句话 | 校验器能抓住的漏网之鱼 |

**P0 出现一次，这一版就不能交付。**

## 三、判定流程（每份样本都要走完）

1. **先建事实库**，人工核对：条目是不是原文有的？动词有没有被美化？
2. **跑诊断**，拿报告
3. **跑校验器** `verify_citations.py / verify.js`，看自动抓到几条
4. **人工逐条过报告**，对照上面六类打标
5. **记录**：按下面的格式写，每条都要有"用户照做会怎样"

第 4 步不能用 AI 自己判——它不知道简历主人真实干过什么。**必须有人工这一层。**

## 四、记录格式

```markdown
### BC-001 · P0 · 编造
- 位置：报告「你手里有什么」第 2 条
- 输出：有独立负责数据分析项目的经验
- 事实库：f-007 原文为「参与数据整理」
- 判断：编造。"独立负责"在简历里没有任何出处
- 用户照做会怎样：面试被追问"你独立做的部分是什么"时答不上来
- 修法：动词必须回落到原文；校验器的 VERB_UPGRADE 应覆盖"独立"
- 状态：已修 / 未修
```

## 五、每次分析完要回答的三个问题

1. **这一版 P0 有几个？** 有就不交付。
2. **错误集中在哪一步？** 建事实库 / 分类 / 改写。集中说明是那一步的提示词有问题，不是全局问题。
3. **有没有一类错误是校验器抓不到的？** 有就说明需要新规则，把它写成可执行判断，而不是写进提示词。

## 六、诚实原则

样本是虚构的、或者用了作者自己的简历，都要在报告里写明。
**用自己简历测出来的 bad case，只能证明"模型会犯这类错"，不能证明"真实用户会遇到"。** 这两个结论不要混。
