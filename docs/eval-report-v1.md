# 提示词 v0.1 实测报告（5 份样本）

> **测试日期**：2026-11-02
> **被测对象**：`04-原型/提示词-v0.1.md`
> **样本**：`06-评测/测试样本-5份-虚构.md`（5 份虚构简历 + JD，附埋点表）
> **执行方式**：AI 严格按 v0.1 的两段提示词处理每份样本

---

## 0. 先说这个方法本身的问题（很重要）

**这 5 份样本带答案（埋点表），所以我读答案再跑，等于开卷考试。**

这意味着本报告的结论边界：

| 能验证 | 不能验证 |
|---|---|
| ✅ 输出格式能不能稳定产出 | ❌ 产品对真实用户有没有用 |
| ✅ 判断逻辑能不能覆盖不同类型的问题 | ❌ 遇到没标答案的简历，能不能找出真问题 |
| ✅ 提示词的哪些约束会失效 | ❌ 真实用户看不看得懂、愿不愿意改 |

**要真验证，必须用不带答案的简历。** 下一轮应该拿 3 份真实简历（可以从戴自己的、同学里收），只给简历和 JD，让我出报告，然后**由戴或用户本人判断"这条我原来没想到"**——那才是真信号。

所以本报告只解决一个问题：**v0.1 的骨架对不对，哪里会漏。**

## 1. 五份的诊断结果

### 样本 1｜李思远 → AI 产品经理实习 —— 【C 类 · 资格型】

| JD 要的（4 条） | 强度 | 依据 |
|---|---|---|
| ① 需求调研 + PRD + 原型 | **无** | 简历全文无"需求文档""原型"任何痕迹 |
| ② Prompt 迭代 + 评测集 + 指标 | **无** | 无任何 AI 应用、无 LLM 相关项目 |
| ③ 数据归因（跟踪使用数据做问题归因） | 中 | [f-005] 12 期反馈周报 + [f-002] 留存 62%→70%，有数据手感但没做过归因 |
| ④ 跨职能协作推动 | 中 | [f-006] 周报被运营组采纳为迭代依据 |

**真问题**：
- **主缺陷（硬门槛缺失）**：JD 明确写"自己搭过 AI 应用或系统写过 Prompt 者优先"、"能写清楚一份 PRD"，这两条他一条都没有。**这不是简历措辞问题，是资格问题。**
- **次缺陷**：唯一真实可迁移的支点是「用户运营」——社群 60+ 条/日咨询是**一手用户需求来源**，12 期周报是**需求归纳**。这段经历的真正价值不是"运营"，是"离用户最近"，但简历里写成了纯执行。

**该不该改简历**：**先别改。** 先做出一个能拿出来看的 AI 产品（哪怕很小），再回来改。现在改措辞，面试第一问"你搭过什么"就会露底。

**投递策略**：AI 产品实习 → 改成「AI 产品运营实习 / 用户运营实习（AI 方向）」，这条路径他现有的经历够用，且是同一批公司的同一个门。

### 样本 2｜王琳 → 数据分析师 —— 【C 类 · 资格型（最严重）】

| JD 要的（4 条） | 强度 | 依据 |
|---|---|---|
| ① SQL 熟练（多表关联、窗口函数） | **无** | 技能栏无 SQL，全程用生意参谋后台导出 |
| ② Python / R 之一 + BI 工具 | **无** | 只有 Excel、PPT |
| ③ 异动归因 + 专项分析 | 弱 | [f-012] 140+ 期周报，是"导出→制作"，不是"分析→归因" |
| ④ 电商/零售行业经验 | **强** | [f-010] 4 年天猫运营 + [f-014] 竞品价格带对比 |

**真问题**：
- **主缺陷（硬技能不达标）**：JD 的第一条硬要求是 SQL 熟练（点名窗口函数），第二条是一门建模语言，第三条是 BI 工具。他 4 条硬技能里 0 条具备。**改简历 100% 救不了。**
- **这份简历最危险的地方**：它有 4 年工作经历 + 电商背景，看起来"很匹配"，容易让改简历类工具给出"优化技能栏"这种害人建议。

**该不该改简历**：**不该。** 改简历只会让他去投一批必挂的岗位。

**真正的路（这才是他需要的）**：
1. 补 SQL 到能写窗口函数（约 4–6 周，每天 1 小时，LeetCode 数据库题 + 牛客 SQL 篇）
2. 学一个 BI 工具（Tableau Public 免费，2 周）
3. 做 1 个能展示的分析作品：用他自己店铺的真实数据（脱敏），做一份"双 11 价格带与转化率关系"分析
4. 目标岗位从「数据分析师」调整为「电商数据分析师 / 商家运营分析」——4 年电商背景是资产，别浪费

**给用户的实话**：这个岗位他现在投不了，但 2 个月后可以。**不是"你不适合"，是"你还没装这个零件，装上就能跑"。**

### 样本 3｜陈嘉豪 → 用户增长运营 —— 【B 类 · 重构型】

| JD 要的（4 条） | 强度 | 依据 |
|---|---|---|
| ① 全链路增长方案设计 | 弱 | [f-016] 20+ 场活动，全是"配置与上线"，是执行不是设计 |
| ② A/B 测试 + ROI 评估 | **无** | 简历无任何 A/B 测试、ROI、投放数据 |
| ③ 漏斗拆解 + 归因 | 弱 | [f-018] "每日跟进核心指标，异常同步上级"——发现异常但没做归因 |
| ④ 跨团队推动产品化 | 中 | [f-019] SOP 文档 + [f-020] 对接设计/开发/审核 |

**真问题**：
- **主缺陷（成果零量化 + 全程被动）**：5 条 bullet 的动词是「执行、配合、参与、协助、对接、同步」。**没有一条是他自己判断了什么、决定了什么。**
- 这份的坑在于：**这不是"改 3 句话"能解决的，需要整段重构；但重构又需要他真的有判断，否则就是编。**

**⚠️ v0.1 在这里会出错**：v0.1 会直接给出改写建议（比如"把'配合完成 20+ 场活动'改成'主导 20+ 场活动的策略设计与落地'"）——**这是逼用户编造，违反 PRD 的第一条铁律。**

**正确做法（v0.2 要加）**：先反问，不许直接改：
> 「这 20 多场活动里，有没有哪一场是你自己决定了'怎么做'的？比如选哪个玩法、定哪个奖励、怎么分层。哪怕是很小的一个决定，告诉我是哪件、你当时怎么想的。」

外包岗也一定有过自主判断的时刻，只是他自己不觉得那算"负责"。**问出来才有得写，问不出来就该承认这份经历确实单薄。**

### 样本 4｜赵一鸣 → B 端产品经理（HR SaaS）—— 【A 类 · 措辞型】

| JD 要的（4 条） | 强度 | 依据 |
|---|---|---|
| ① B 端复杂业务抽象（多角色权限、流程配置） | 中 | [f-022] 3 个模块 120+ 需求，但未说明是否涉及权限/流程 |
| ② 客户访谈 + 售前对话 | **无** | 简历无任何客户接触记录 |
| ③ PRD + 原型 + 交付质量 | **强** | [f-024] 60 份 PRD、200+ 页原型、[f-026] 按期交付率 90% |
| ④ 商业化理解（ARR、续费率） | **无** | 无任何收入/续费相关表述 |

**真问题**：
- **主缺陷（过程指标冒充成果）**：120 个需求、60 份 PRD、200 页原型、40 次评审——**全是工作量，没有一条业务结果。** 这是他最吃亏的地方：干了 5 年，简历读起来像个高效的执行机器，不像个产品经理。
- **次缺陷（行业纵深缺失）**：协同办公 ≠ HR SaaS。JD 要"HR SaaS/ERP 优先"，他是零。

**该不该改简历**：**该改，而且这是 5 份里唯一一份改简历就能明显提升的。**

**哪几句该怎么改（落到具体句子）**：

**① 原句**：`负责协同办公产品 3 个模块的需求设计与迭代，累计上线需求 120+ 个`
**建议**：`负责协同办公产品 3 个模块的需求设计与迭代。其中一个模块（填写模块名）上线后，把原来需要 X 步的操作压到 Y 步，客户使用该模块的人数从 A 涨到 B`
**理由 + 依据**：[f-022] 有模块和需求数，但缺结果。**先删掉"120+"这个数**——需求多不等于价值大，反而是负分。换成"哪个模块 + 改了什么 + 谁受益"。
> ⚠️ 如果拿不到使用数据，退化写法：`负责 XX 模块，解决的客户问题是：原来 A 角色要手工做 X，现在系统自动完成`

**② 原句**：`独立完成 PRD 撰写 60 余份，输出原型图 200+ 页`
**建议**：直接删掉这句话。
**理由**：PRD 份数是最没信息量的指标，任何 B 端 PM 都能写 60 份。留着占位置，还暗示"我只会写文档"。

**③ 原句**：`建立需求池管理机制，规范需求优先级评估流程`
**建议**：`建立需求池管理机制，把原来"谁嗓门大谁先做"的排期方式，改成按 XX 维度打分排序，评审会上争议减少（可写具体：单次评审时长从 2 小时降到 40 分钟）`
**理由 + 依据**：[f-025] 这是全篇最有价值的一条——它证明他有"改机制"的能力，不是纯执行。但现在写成了空话，必须加"改之前是什么样"。

**④ 原句**：`参与竞品分析，输出竞品功能对照表 5 份`
**建议**：删掉，或改成"用竞品对照表推动过 1 个功能立项（哪个功能）"
**理由**：对照表是动作不是结果。没推动过决策的竞品分析，等于没做。

**不用改的句子**：
`组织需求评审会 40 余次，跟进研发排期与测试验收，需求按期交付率 90%` —— **这句留着，写得很好。** 90% 按期交付率是实打实的交付能力证明，而且"跟进排期 + 测试验收"是 B 端 PM 的核心动作。

**投递策略**：HR SaaS 直接投会被"行业经验"卡。改投「协同办公 / 企业服务 / 项目管理 SaaS」的 B 端 PM，他的经历完全够，而且 5 年经验能上 senior。

### 样本 5｜孙雅 → 新媒体内容运营 —— 【C 类 · 资格型，但可迁移】

| JD 要的（4 条） | 强度 | 依据 |
|---|---|---|
| ① 内容产出 + 爆款能力（10w+ / 50w+） | 弱 | [f-031] 87 篇 / 1200 粉 / 最高 460 赞 —— 与 10w+ 差约 200 倍 |
| ② 平台机制理解（小红书/抖音规则） | 弱 | 有个人号在跑，说明有手感，但没有方法论层面的表述 |
| ③ 达人合作 + 投放 ROI | **无** | 无 |
| ④ 拍摄 + 剪辑 + 脚本 | 弱 | 剪映基础、秀米排版 |

**真问题**：
- **主缺陷（经验完全不对口 + 爆款不达标）**：行政岗 vs 新媒体岗，个人号 460 赞 vs JD 要 10w+。
- **但这份有真东西**：87 篇持续更新（执行力）+ 公文撰写（结构化表达）+ 6 场 200 人活动（策划落地）+ 内部公众号 50 余篇（企业内容）。**这四条是可迁移的，不能一句"不合适"打死。**

**该不该改简历**：**现在改没用，3 个月后再说。**

**3 个月补法（这是她真正需要的，必须具体）**：
1. **第 1 个月**：选定 1 个品类（她已经在做家居好物，别换），拆 10 篇该品类爆款笔记——每篇记录：选题角度、封面结构、标题句式、发布时间。产出一份《家居好物爆款拆解 10 篇》
2. **第 2 个月**：用拆出来的规律做 6 篇实测（每周 1–2 篇），记录数据
3. **第 3 个月**：把数据最好的一篇做到极致（同选题换 3 个封面/标题做对比），争取单篇破 5000 赞
4. **简历改法**：把「行政专员」重构为「内容与活动运营」，突出公文撰写→文案能力、活动组织→策划落地、内部公众号→企业内容运营，个人号放最前面但**不吹数字**，写"持续更新 87 篇，最高单篇 460 赞，正在做爆款方法论拆解"

**给用户的实话**：这个岗位现在投不了，差的是"一个能证明你能做爆款的案例"。3 个月能补上，因为底子（写作、策划、执行力）都在。**不是"你不适合"，是"你还没有一个能被看见的作品"。**

## 3. v0.1 暴露的四个硬伤（这才是本次测试的真收获）

### 硬伤 1 · 事实库门槛设错了（≥20 条不现实）

v0.1 写「条目数 ≥20，少于 20 条说明简历信息太少」。

实测：**5 份里没有一份能拆到 20 条**。样本 4 内容最多，也只能拆出 9 条（教育 1 + 3 个模块各 2 + 机制 1 + 竞品 1）。真实学生的简历通常 6–10 条。

**后果**：如果严格按 v0.1 执行，5 份全部会被判"信息太少，案例放弃"——**工具直接罢工**。

**改成**：≥8 条为合格，6–7 条提示"信息偏少，结论会偏保守"，≤5 条才放弃。

### 硬伤 2 · 没有"可救性判断"这一层（最致命）

v0.1 拿到简历就直接进四段（岗位要什么 → 你手里有什么 → 缺什么 → 哪几句怎么改）。

**问题**：样本 2 根本没有能力，v0.1 的第四段还是会给出改写建议——**给一个 SQL 零基础的人改简历去投数据分析师，等于推他进坑。**

**这是产品的生死线**：一个只会改措辞的工具，和一个能判断"你现在不该投这个岗位"的工具，是两个物种。后者才是 PRD 里写的那个"告诉你缺什么"。

**改成**：进入四段之前，先做三分类：

| 类型 | 判据 | 输出什么 |
|---|---|---|
| **A 措辞型** | 核心能力都有证据，只是没写清 | 正常四段 + 逐句改写（样本 4） |
| **B 重构型** | 经历够，但角色定位写成了执行者 | 先追问"哪件是你自己决定的"，问到了才重构（样本 3） |
| **C 资格型** | 核心能力里 ≥2 条完全没有证据 | **不逐句改写**，只输出"缺什么零件 + 多久能补上 + 先投什么岗位"（样本 1、2、5） |

### 硬伤 3 · B 类会逼用户编造

v0.1 的改写是"给建议"，模型看到"配合完成 20+ 场活动"很自然会改成"主导 20+ 场活动策划"。**用户念着爽，面试一追问就崩。**

这和 PRD 第一条铁律（不编造）直接冲突，而且 v0.1 的约束拦不住——因为模型不认为这是编造，它认为这是"表达优化"。

**改成**：
1. 改写前必须先有"用户自己的判断"作为原料。没有原料就不改，改为提问。
2. 新增一条硬约束：**改写只能重组用户已有的信息，不能升级动词。** 「参与/协助/配合」不许改成「主导/负责/独立完成」，除非事实库里能指到对应的自主决策证据。

### 硬伤 4 · 缺"可迁移项"和"时间账"

样本 5 的正确输出不是"你不合适"，而是"可迁移的有这 4 条 + 补 3 个月能到线"。v0.1 没有这个字段，模型只会给"缺什么"，容易写成判决书。

**改成**：C 类输出强制包含两栏——
- **可迁移项**：现有经历里哪些能力能带过去（必须指向具体事实编号）
- **时间账**：补齐最短路径需要多久（要给月数，不许写"尽快"）

## 4. 结论

**v0.1 的骨架是对的**（事实库 → 强度判断 → 缺口 → 改写，四段逻辑成立，埋点能命中）。

**但它只覆盖了 A 类（措辞型）**。真实场景里，5 份样本中 A 类只有 1 份（样本 4），占 20%。**另外 80% 是 B 类和 C 类，v0.1 要么给错建议，要么逼用户编造。**

这个比例值得警惕：如果真实求职者里也是 4/5 属于"资格不匹配"，那这个产品的核心价值其实不是"改简历"，是**"告诉你现在该投什么、该补什么"**。

**这可能意味着定位要微调**——从"简历优化助手"往"投递决策助手"偏一点。但先别急着改定位，等 3 个真实案例跑完再判断（样本是虚构的，比例未必真实）。
