# Badcase 归因档案

> 这个产品上线前后抓到的每一个坏案例，按发现时间排。每条都有：现象 → 归因 → 修法 → 还没解决什么。
> 写这份档案的原因很简单：**评测和归因是 AI 产品经理的核心手艺，而手艺只能在真实坏案例上练。**
> 下面没有一条是编造的测试用例，全部来自真实运行。

## P0 级（用户会拿到错误结果，且毫无提示）

### BC-01 静默空报告

- **现象**：`deepseek-v4.1-flash` 跑诊断，返回了分类（C）和理由，但 rewrites / gaps / evidence 全是空数组。页面显示「诊断完成」，用户拿到一份什么都没说的报告。
- **归因**：输出校验只查了「有没有 class 字段」，没查「这个分类该有的内容段落有没有」。模型偷懒时，最小合规输出就能骗过校验。
- **修法**：按分类定硬条件——A/B 类必须 `rewrites + gaps > 0`，C 类必须 `gaps + transferable > 0`。不满足自动换模型重跑（最多 3 个，单个 30 秒超时）。
- **教训**：**校验「格式合规」不等于校验「内容有效」。** 每种输出类型都要问一句：它偷懒的最小输出长什么样，我的校验拦不拦得住。

### BC-02 五分钟无响应

- **现象**：真实用户（作者本人）跑诊断，等了五分钟没结果，跳走页面，任务丢失。
- **归因**：代码写的是「取模型清单第一条」，而第一条 `auto` 是推理模型、思考强度 high——实测**首字延迟 206 秒**。它三分钟还没开口，用户当然走。
- **修法**：33 个模型全部实测同一份输入，按「首字延迟 + 输出完整度」选型，`glm-5.3-flash` 全程约 17 秒。
- **教训**：**模型快慢只能实测，不能靠元数据字段推断。** 我曾按「强制思考 = 肯定慢」排除模型，结果把最快的误排除、留下了会输出空报告的。这条写进了代码注释。

## P1 级（结果错误但用户能察觉）

### BC-03 Figma 只提醒、不删除

- **现象**：技能栏写了「原型设计（Figma）」，但六个项目的原型物证全是 HTML 线框图。第一版输出只在结尾「提醒了一句」，技能栏原样保留。
- **归因**：提示词里写了「提醒用户核对」，模型选择了最小阻力路径——提醒比删除安全，它当然提醒。
- **修法**：提示词改为「只在技能栏自述、经历里找不到证据的，**必须删掉**，提醒不算数」。
- **教训**：**你让模型「提醒」，它就只会提醒。** 想要什么行为，就把那个行为写成硬性产出。

### BC-04 假改动凑数

- **现象**：改动清单报了 8 条，其中 2 条的「原句」和「新句」去掉标点后一字不差。
- **归因**：输出格式要求「最多 8 条改动」，等于给了凑数的激励；没有校验改动是否真实发生。
- **修法**：后处理加 norm() 归一化去重，原句新句一致的一律过滤。
- **教训**：**给数量上限就是邀请凑数。** 数量指标必须配内容校验。

### BC-05 微信号照抄进简历

- **现象**：生成简历里直接复制了原简历的真实微信号。
- **归因**：提示词从头到尾没有关于联系方式的规定。模型没有隐私概念，原文有什么它抄什么。
- **修法**：铁律加「手机/邮箱/微信一律占位符」，并在纯净度检查里查真实号码特征。
- **教训**：**模型不知道你的顾虑，除非你写出来。** 每一条铁律背后都是一次真实翻车。

### BC-06 诊断报告里的黑话

- **现象**：诊断报告输出了「闭环」「对齐」——这两个词是用户明令禁止的。
- **归因**：禁用词表只写进了**简历改写**的提示词，**诊断**的提示词漏了。同一个约束要写在每一个会输出文字的环节。
- **修法**：两段提示词都加禁用词表，另加自动黑话检查（只查正文，不查引用原文的句子）。

## P2 级（产品方向错误——用户教的）

### BC-07 对单份 JD 定制化

- **现象**：第一版设计是「输入一份 JD，改一份简历」。用户原话：「我不可能遇到一个 JD 给你一张纸帮我改一次，再遇到一个再改一次。」
- **归因**：**产品假设错了，不是功能错了。** 求职者的真实用法是拿一份简历投一类岗位。对单份 JD 定制 = 每投一家都要回来跑一次 = 没人会用。
- **修法**：默认改成类适配模式——从 6 份在招 JD 提炼「类岗位需求库」（硬要求 H / 高频加分 P / 深层要求 D 三层），简历按类优先级排证据；具体 JD 只用来补特别要求。
- **教训**：**这一条不是测试测出来的，是用户说出来才知道的。** 产品假设再自洽，也要拿真实使用方式对一遍。

### BC-08 把「没回音」当「简历有问题」

- **现象**：用户担心「投完三四天没人鸟，是不是简历有问题」。
- **归因**：判定边界没写清。投递无回音是高噪声信号——招聘方可能根本没看（HR 一天几百条消息、已读不回是常态）、岗位已满还在挂、投递时间不对。把它当简历的评价指标，会误导迭代方向。
- **修法**：诊断提示词写死判定边界「只判断人岗匹配，不预测回音」；诊断报告固定附带一段「关于投了没回音」，写明什么时候才该怀疑简历（同类岗位 10 家以上、多数已读仍无回复）。

### BC-09 同输入分类漂移

- **现象**：同一份简历 + 同一份 JD 连跑两次，一次判 B（改改能投），一次判 C（先别投）——两个结论对用户是相反的行动指令。
- **归因**：三分类判据目前是描述性语言（"无 ≥2 条 → C"），边界附近的样本模型自由裁量。
- **修法**：部分解决——类需求库把要求编了号（H/P/D），判据从"模型体会"往"数编号"挪。
- **未解决**：分类仍是模型判断，没有做到完全确定性。页面和文档已明示「分类仅供参考」。下一步是把 A/B/C 改成可计算的硬条件。

## 修复优先级怎么定的

P0 = 用户拿到错误结果且无提示（信任问题，当天修）
P1 = 结果错误但可察觉（质量问题，当天修）
P2 = 产品方向错误（只有真实用户能发现，发现即改方向）

三条规律，也是这份档案的结论：

1. **P0 全是"静默失败"**——系统没崩、没报错，只是悄悄给了个错的。做 AI 产品最该防的就是这类。
2. **P1 全是"提示词没写到"**——模型的每个偷懒路径，都是你没堵上的口子。
3. **P2 只能靠真实用户**——我自己测一百遍也测不出 BC-07，因为我会顺着产品设计用它。
