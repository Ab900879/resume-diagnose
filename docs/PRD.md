# 简历优化助手 · PRD v1.0（可验证版）

> **文档状态**：可执行。含 3 处「待验证」，每处都写明了用什么动作验证、判定线是多少。
> **取代**：`产品定位假设 v0.1` + `产品输出规格 v0.1`（两份合并，旧文件保留作过程记录）
> **编写**：张照泉（判断与取舍） / AI（结构初稿、概念解释）
> **这一版改了什么**：把「想法」改成了「可以被判对错的需求」——每一条功能都带**判定方式**和**通过线**。

---

## 0. 一页纸摘要

给一个正在找实习的学生一份简历、一个 JD，它输出四段内容：**这个岗位要什么 → 你手里有什么 → 你缺什么 → 哪几句具体该怎么改**。

每一句改写都必须带事实编号，指回用户原文；**指不回去的句子一律不输出**。

不做美化、不打分、不生成整份简历。第一版只服务一个人（我自己），只验证一件事：**照着它改，面试邀约会不会变多。**

## 1. 用户

### 1.1 主用户（必须具体到一个人）

**2027 届本科生，第一次认真找实习，投了十几家没有回音，不知道简历哪里出了问题。**

为什么必须这么窄：范围一放宽到「所有求职者」，需求就会退化成「帮我把简历写得更好看」——那是润色工具，不是这个产品。

### 1.2 三个用户画像假设（**待验证，P0 阻塞项**）

| # | 假设 | 如果错了会怎样 |
|---|---|---|
| P1 | 他手上有一段**真实但没写清**的经历（做完了但没写数字/没写结果） | 如果他的经历本身是空的，产品给的建议全变成「去补经历」，不是改简历能解决的 |
| P2 | 他已经有一版改过 2 次以上的简历，而不是从零开始写 | 如果是从零开始，他需要的是模板，不是诊断 |
| P3 | 他愿意花 30 分钟读一份「说你缺什么」的报告 | 如果只想听好话，第三段（缺口）会直接劝退——这是最大风险，见 §9 H2/H3 |

**验证动作**（阶段 0，2 天）：找 3 个正在找实习的同学，只问一句：
> 「你上次改简历的时候，最纠结的是哪一句？最后怎么改的？」

**判定线**：3 人中有 ≥2 人能说出一句**具体的、纠结过的句子**（不是「整体感觉不好」），P1 和 P2 视为成立。

### 1.3 明确不服务谁

- 工作 3 年以上的社招（他们的简历逻辑是业绩数字，不是能力证据）
- 完全没经历、需要「从零包装」的人（我们的底线是不编造，这类用户会失望）
- 想要一键生成整份简历的人（对应 §3 第 3 条）

## 2. 问题

### 2.1 问题陈述（**待补用户原话**）

**当前版本（假设）**：
> 学生不确定「自己手里的经历够不够这个岗位」，也不确定「该写哪一段、写到什么程度」。于是他要么堆所有经历，要么反复润色措辞——**改的都不是 HR 真正在筛的那一层。**

**待补**：3 条用户原话。填入前这段话不成立，只能说「我猜」。

### 2.2 现有替代方案，以及它们失效在哪

| 他现在的做法 | 失效点 |
|---|---|
| 直接把简历丢给 ChatGPT「帮我改改」 | 没有 JD 作参照 → 只能润色措辞，不能判断匹配度；越不确定越容易被它编 |
| 看学长/网上的模板 | 模板解决格式，不解决「我这段经历算不算数」 |
| 问 HR 朋友 | 有效但不可复用，且只能问一次 |
| 自己想 | 缺的是外部标准，不是努力 |

**这一列是本产品的存在理由**：以上方案里，**没有一个会告诉你「这条你没有证据」**。

### 2.3 问题的可验证性

这个问题是否真实，不靠讨论，靠一个动作验证：

> 让 3 个目标用户各自拿出简历，问：「如果现在有个工具告诉你哪几句该改，你希望它先说哪一句？」

- 回答指向**具体句子** → 问题成立
- 回答指向**整体感觉 / 排版 / 用什么模板** → 问题不成立，产品方向要改

## 3. 不做什么（五条，缺一条都不算 PRD）

| # | 不做 | 理由 |
|---|---|---|
| 1 | **不编造、不拔高任何经历** | 唯一判据：面试官追问三层，用户还站得住吗。站不住的建议等于害他 |
| 2 | **不打总分、不给百分比匹配度** | 分数会诱导用户刷分（改措辞把分刷上去），而不是去补真实缺口。**分数是假的可验证性** |
| 3 | **不自动生成整份简历** | 用户不会逐句读，出了事他不知道哪句不是自己的。责任必须留在用户手里 |
| 4 | **不爬招聘网站** | 违反平台协议、涉个人信息保护法。见 `需求拆解与排期.md` 第五节。手动粘贴 JD 零风险且工作量只有十分之一 |
| 5 | **第一版不做界面** | 内容对不对还没验证，做界面等于给没想清的东西化妆。先出 Markdown 报告 |

## 4. 什么叫「做好了」

### 4.1 北极星指标

**改造后简历的「面试邀约率」，相对基线的提升。**

选它的理由：这是唯一一个「用户真的因此受益」的指标。满意度、NPS、生成次数都能刷，邀约率不能。

### 4.2 三条可测判据（MVP 通过的硬线）

| # | 判据 | 测法 | 通过线 |
|---|---|---|---|
| A1 | **零编造** | 人工逐句核查输出，每句能否指回原文 | **100%**。出现 1 句无来源即不合格（这是生死线，不允许打折） |
| A2 | **判断有用** | 3 个真实用户各看一份报告，问「这份报告里有没有一句话是你原本没想到的」 | 3 人中 ≥2 人说「有」，且能指出是哪一句 |
| A3 | **行为改变** | 3 个真实用户中，实际按建议改了简历的人数 | ≥1 人真的改了（不是「觉得有道理」，是动手改了） |

### 4.3 反指标（出现即判定失败）

- 报告里出现用户简历中不存在的数字、公司名、时间
- 用户看完说「所以我的简历到底几分」（说明它在被当成分数工具用）
- 用户照着改了，但改出来的句子他自己解释不了（说明建议太"高级"，超出他的真实水平）

## 5. 功能需求

> 优先级：**P0 = 没有它产品不成立**；P1 = 有它才可用；P2 = 可以没有。
> 每条都写了「怎么验」，不是「要做什么」。

### F1 · 建立事实库（P0）

**用户故事**：作为用户，我把简历里的每段经历拆成带编号的条目，之后所有改写只能引用这些编号。

| 项 | 内容 |
|---|---|
| 输入 | 一份简历（docx / pdf / 纯文本） |
| 输出 | N 条事实条目，字段见 §6.1 |
| 验收标准 | ① 条目数 ≥30；② **每条都带 `来源`（简历第几段第几行）**；③ 每条标了 `可验证性`（高中低）；④ 术语与数字写进 `禁止改写` |
| 怎么验 | 随机抽 5 条，回到简历原文能逐字对上。对不上 = 编造，直接不通过 |
| 通过线 | 抽检 5 条，5 条全部对得上 |

**为什么这是 P0**：它是唯一不可替代的资产，也是防编造的地基。换成提示词「禁止编造」= 只是请求，模型可以不听，而且无法验证。

### F2 · 从 JD 抽出能力要求（P0）

| 项 | 内容 |
|---|---|
| 输入 | 目标 JD 文本（手动粘贴） |
| 输出 | **3–5 条**能力要求，按重要性排序，每条带一句「这个岗位为什么看重它」（引 JD 原文） |
| 验收标准 | ① 数量在 3–5 之间（**超过 5 条即不合格**，20 个关键词等于没有重点）；② 每条能指回 JD 的某一句；③ 不允许输出「沟通能力强」这类无法验证的套话，除非 JD 原文写了 |
| 怎么验 | 拿 3 个真实 JD 各跑一次，人工核对每条是否能指回原文 |
| 通过线 | 3 个 JD 共 ≈12 条要求，**≥10 条**能指回原文且不属于套话 |

### F3 · 逐条对照，定证据强度（P0）

| 项 | 内容 |
|---|---|
| 输入 | F2 的能力要求 × F1 的事实库 |
| 输出 | 每条能力要求对应一个强度：**强 / 中 / 弱 / 无**，并附用户原句摘录 |
| 验收标准 | ① 每条要求都有结论，不允许跳过；② 判「强」必须给出理由（为什么这条算强）；③ 判「无」时**必须留空，不许硬凑一条接近的** |
| 怎么验 | 自己先独立判一遍，再和系统结论对比。不一致的逐条复盘：是它错，还是我判错 |
| 通过线 | 与人工判断的一致率 **≥80%**（12 条里允许错 2 条） |

### F4 · 缺口结论（P0）

| 项 | 内容 |
|---|---|
| 输出 | 一句话：「这个岗位最看重 N 条，你有 M 条没有证据」，然后给三个选择：换方向 / 补最小证据 / 降低预期 |
| 验收标准 | ① 结论**归因到岗位要求，不归因到人**（❌「你缺乏数据能力」 ✅「这个岗位要数据能力，你现在的材料里没有能证明它的部分」）；② 「补最小证据」必须具体到「做什么、多久、能产出什么」，出现「去实习」「多练练」即不合格 |
| 怎么验 | 把报告给一个不知情的同学看，问「看完这段话，你觉得是在说你不行，还是在说这个岗位要什么」 |
| 通过线 | 3 人中 ≥2 人回答「在说岗位要什么」 |

### F5 · 逐句改写，强制带来源（P0）

| 项 | 内容 |
|---|---|
| 输出 | 每条三段式：`原句 / 建议 / 理由 + 依据（fact_id）` |
| 验收标准 | ① **每一条都有 `依据` 字段，格式 `[f-0xx]`**；② 数字只能原样搬，不许换算、取整、四舍五入；③ `禁止改写` 里的词一个都没变 |
| 怎么验 | 机器可自动校验：正则扫输出，任何一节缺少 `[f-\d{3}]` 即报错。再用脚本比对数字集合（原文数字 ⊆ 输出数字，且无新增） |
| 通过线 | **100% 带来源 + 0 新增数字**。这一条不设容错 |

### F6 · 输出 Markdown 报告（P1）

| 项 | 内容 |
|---|---|
| 输出 | 一个 `.md` 文件，四段顺序固定：岗位要什么 → 你手里有什么 → 缺口 → 改哪几句（含「不用改的句子」） |
| 验收标准 | ① 四段齐全且顺序正确；② 含至少 1 条「这段不用改」的说明；③ 全文无总分、无百分比匹配度 |
| 怎么验 | 结构检查脚本 + 人工通读 |
| 通过线 | 结构 100% 合规 |

**为什么要「不用改的句子」**：明确告诉他哪里不该动，比只说哪里该动更能建立信任——说明产品有边界，不是见什么改什么。

## 6. 数据规格

### 6.1 事实条目（F1 的输出）

```json
{
  "id": "f-014",
  "类型": "项目",
  "内容": "用 SQL 做日/周/月统计报表，上线在用",
  "时间": "2026.01",
  "来源": "简历 PDF · 第 3 段第 2 行",
  "可验证性": "高",
  "禁止改写": ["SQL", "日/周/月", "上线在用"],
  "适用岗位": ["数据分析", "AI 产品运营"]
}
```

| 字段 | 硬性要求 |
|---|---|
| `id` | 全局唯一，不可复用。改写引用它 |
| `来源` | **必填**。指不回原文的条目一律丢弃 |
| `可验证性` | 高=有物证（链接/截图/后台数据）；中=有人能证明；低=只有自己记得 |
| `禁止改写` | 术语、数字、专有名词。模型最容易在这里"优化"出假信息 |

### 6.2 防幻觉的四条硬约束（**机器可校验**）

| # | 约束 | 校验方式 |
|---|---|---|
| 1 | 每句输出必须带 `[f-0xx]` | 正则扫描，缺一个即失败 |
| 2 | 输出中的数字集合 ⊆ 原文数字集合 | 脚本提取两侧数字，做差集，非空即失败 |
| 3 | `禁止改写` 字段里的词必须原样出现 | 字符串包含检查 |
| 4 | 不得出现事实库里没有的专有名词 | 用实体列表做白名单过滤 |

**这四条是「可验证」的核心。** 判断一个 AI 产品靠不靠谱，不看它说了什么，看它的约束能不能被机器查出来。

### 6.3 输出结构

```json
{
  "jd_requirements": [{"id": "r1", "text": "...", "jd_evidence": "JD 原句"}],
  "evidence_map": [{"req_id": "r1", "strength": "中", "quote": "用户原句", "fact_ids": ["f-003"]}],
  "gap": {"total": 4, "missing": 2, "options": ["换方向", "补最小证据", "降低预期"]},
  "rewrites": [{"original": "...", "suggested": "...", "reason": "...", "fact_id": "f-003"}],
  "keep_as_is": [{"text": "...", "why": "..."}]
}
```

## 7. 评测方案（阶段 3）

### 7.1 十条测试用例（必须覆盖三类）

| 类型 | 条数 | 目的 |
|---|---|---|
| 正常案例 | 4 | 验证主流程能跑对 |
| **边界案例** | 3 | 空经历、跨行业投递、JD 极短 |
| **对抗案例** | 3 | 故意诱导它编造（如 JD 要求「有百万粉丝账号」，用户没有） |

**对抗案例是重点**：产品声称「不编造」，那就必须拿出能证明它不编造的证据。**没有对抗测试的"防幻觉"都是宣传。**

### 7.2 打分规则（人工，逐条 0/1，不设中间分）

| 维度 | 判定 |
|---|---|
| 来源可溯 | 每句能指回原文 = 1，否则 0（整份报告一票否决） |
| 判断准确 | 强度判断与人工一致 = 1 |
| 缺口诚实 | 该说「无」的地方没硬凑 = 1 |
| 措辞不伤人 | 归因到岗位而非人 = 1 |

### 7.3 badcase 分类（必须判断归属）

| 类别 | 表现 | 该改什么 |
|---|---|---|
| 检索类 | 事实库里明明有，但没被选出来 | 改检索/排序逻辑，**不是改提示词** |
| 生成类 | 选对了事实，但改写出假信息 | 改约束校验 |
| 规则类 | 输出本身没错，是我的评分标准错了 | 改评分规则 |
| 输入类 | JD 或简历本身残缺 | 改输入校验 |

**通过线**：10 条用例中 ≥8 条通过，且**至少抓住并正确归类 1 个 badcase**。

> 抓 badcase 并判断「是模型的错还是我规则的错」，是这一阶段唯一值钱的东西。它只可能来自看到结果后觉得不对，不来自提示词。

## 8. 端到端验收清单（可勾选）

| # | 检查项 | 方法 | 通过标准 | 结果 |
|---|---|---|---|---|
| 1 | 三份真实简历能跑通 | 手动跑 | 3/3 有输出 | ☐ |
| 2 | 零编造 | 逐句核查 | 100% 可追溯 | ☐ |
| 3 | 数字无新增 | 脚本比对 | 差集为空 | ☐ |
| 4 | 能力要求数量合规 | 数量检查 | 3–5 条 | ☐ |
| 5 | 措辞归因到岗位 | 盲测 3 人 | ≥2 人认为「在说岗位」 | ☐ |
| 6 | 有「不用改」的句子 | 结构检查 | ≥1 条 | ☐ |
| 7 | 无总分、无匹配度百分比 | 全文搜索 | 0 处 | ☐ |
| 8 | 10 条用例通过率 | 跑评测 | ≥8/10 | ☐ |
| 9 | badcase 已归因 | 人工判断 | ≥1 个，类别明确 | ☐ |
| 10 | 真实用户改了简历 | 回访 | ≥1 人 | ☐ |
| 11 | 邀约率对照 | 20 家基线 vs 20 家实验 | 实验组高于基线 | ☐ |

**第 11 条是最终的，也是最容易被跳过的。没有基线的改版等于没改——你不知道是真提升了还是运气。**

## 9. 风险与未验证假设

| # | 假设 | 风险 | 验证动作 | 判定线 |
|---|---|---|---|---|
| H1 | 真痛点是「不知道写什么」，不是「写得不好」 | 低 | 问 3 人一句话（§1.2） | ≥2 人说得出具体纠结的句子 |
| H2 | 用户愿意听「你缺 X」 | **高** | 报告给 3 人看，观察反应 | ≥2 人看完愿意继续聊，而不是关掉 |
| H3 | 指出缺口能带来行动，不是劝退 | **高** | 看是否有 ≥1 人真的动手改 | ≥1 人改 |
| H4 | 改造后邀约率会提升 | 中 | 20 vs 20 对照投递 | 实验组邀约数 > 基线 |

**H2 和 H3 是最大两个坑。** 如果验证下来用户只想要安慰，这个定位要改——要么改成「先肯定再指缺口」，要么承认这个产品做不成。**承认做不成，也是产品经理的合格答案。**

## 10. 版本计划

| 版本 | 范围 | 明确不做 |
|---|---|---|
| **v0（本次）** | 事实库 + 单岗位改写 + Markdown 报告 | 界面、多用户、爬虫、推送 |
| v1 | JD 批量粘贴解析 + 匹配度对照 | 仍然不爬站 |
| v2 | 多用户、自动采集 | 只有在 v0 有稳定用户后才考虑 |

**v0 的隐藏验证价值**：如果连我自己都不愿意每天粘 5 条 JD，说明这个需求是假的——**那时应该停掉项目，而不是继续做。**

## 11. 这份 PRD 怎么被验证（元层面）

PRD 本身也要可验证。三条：

1. **能被非技术的人读懂**：给一个不懂技术的同学看 §1–§4，他能说出「这是给谁做的、不做什么」→ 通过
2. **每条需求都有判定方式**：§5 六条功能全部有「怎么验」和「通过线」→ 已满足
3. **失败时能定位**：出问题时能指回是 F1–F6 哪一条不合格，而不是「感觉不太行」→ 已满足
