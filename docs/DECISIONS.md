# 决策日志

> 这个文件是本项目最重要的产出。
>
> 代码可以由 AI 生成，但「在两个选项之间为什么选了这个」只可能来自我自己。
> 每一次决定都写在这里，包括后来被证明是错的那些——**错的决定不删，加一行「后来发现」**。

---

## 格式

```
## D-序号 · 日期 · 一句话结论
背景：当时面对什么情况
选项：考虑过哪几个，各自的代价
定了：选了哪个
理由：为什么是它，不是另一个
代价：这个选择放弃了什么
后来发现：（留空，事后补）
```

## D-001 · 2026-10-27 · 从真实用户开始，不从代码开始

**背景**：手上已经有六个 AI 生成的项目，全部没有用户。HR 的反馈是「没有真正做过自己的产品」。

**选项**
| 选项 | 代价 |
|---|---|
| 直接重写代码，做一个功能更全的版本 | 快，但还是没有用户，等于第七个 demo |
| 先找三个正在找实习的同学，拿到真实简历和真实困惑 | 慢两天，可能被拒绝，而且这一步 AI 帮不上 |

**定了**：先找用户。

**理由**：产品不是功能多，是有人用。没人用的东西叫 demo。上一版之所以失败，不是代码不行，是没有人需要它。

**代价**：前两天没有一行代码，看起来像没在干活。

## D-002 · 2026-10-27 · 不爬招聘网站，改手动粘贴 JD

**背景**：原设想是自动采集 BOSS 直聘、智联的新增岗位 JD，入库后做匹配推送。

**选项**
| 选项 | 代价 |
|---|---|
| 写爬虫抓岗位 | 违反平台用户协议；规模化可能触及《反不正当竞争法》；JD 常带 HR 姓名电话，受《个人信息保护法》约束；还要对抗反爬 |
| 官方开放 API | 需要有商务资格，个人拿不到 |
| 用户手动粘贴想投的 JD | 每条要手动操作，体验差；但零风险，工作量只有爬虫的十分之一 |

**定了**：手动粘贴。

**理由**：爬虫的难点不是技术，是法律。「能不能做」和「该不该做」是两个问题，产品经理的主要工作是回答后一个。

**代价**：放弃了「自动发现新岗位」这个卖点。可能少掉一批懒的用户。

## D-003 · 2026-10-27 · 「不许编造」用结构强制，不用提示词

**背景**：核心卖点是不能替用户编经历。最初想法是在提示词里写「禁止虚构」。

**选项**
| 选项 | 代价 |
|---|---|
| 提示词写「禁止编造」 | 一行字就完成，但只是请求模型，它可能不听，而且无法验证是否听了 |
| 每条经历建成带编号的事实条目，输出每句必须引用编号，挂不上就删 | 要多设计一层数据结构，写起来麻烦；但错了能被抓出来 |

**定了**：结构强制。

**理由**：请求和强制的区别，就是「聊天」和「产品」的区别。能被验证的约束才算约束。

**代价**：短期内实现变复杂，而且事实库得人工整理，不能全自动。

## D-004 · 2026-11-02 · PRD 用「判定方式 + 通过线」结构，不用需求清单

**背景**：PRD v0.1 只有「产品输出什么」的描述，没有任何一条能判对错。做完了无法判断是否达标。

**选项**

| 选项 | 代价 |
|---|---|
| 继续写功能清单（要做什么） | 熟悉、写起来快；但做完之后只能靠"感觉好不好"验收，等于没验收 |
| 每条需求强制带「怎么验 + 通过线 + 反指标」 | 写起来累，有些需求必须承认"现在无法验证"；但错了能定位到具体哪一条 |

**定了**：后者。

**理由**：一份不能判对错的 PRD，本质是许愿清单。能验收的才叫需求，不能验收的叫期望。而且难写恰恰说明这块没想清——**写不出通过线的地方，就是产品的空洞。**

**代价**：PRD 变长（331 行），且有三处只能标「待验证」，看起来不完整。但这三处是诚实的空洞，不是假装填满。

## D-005 · 2026-11-02 · 先做人力版，不做代码版；竞品拆解降级

**背景**：PRD 定稿后，团队按常规顺序应该先做竞品拆解 → 原型 → 实现。但项目已经停摆 6 天，零代码零用户。

**选项**

| 选项 | 代价 |
|---|---|
| A 按顺序：竞品拆解 → 写代码 → 内测 | 看起来很正规；但要 2–3 周才见到第一个用户，且用户反馈会推翻前面一半工作 |
| B 直接写代码做一个网页 | 有"产品"的样子；但输出长什么样都还不知道，等于给空心想法做装修 |
| C 人力版：自己跑提示词，服务 3 个真人 | 不像"做产品"；但 1 天内能见到真实反馈，且反馈能直接改提示词 |

**定了**：C。

**理由**：
1. 项目真正的空洞不是"没有代码"，是"没有人用过"。代码解决不了后者。
2. 人力版产出的三样东西（真实输出样式、迭代过的提示词、用户反馈）恰好是写代码的前置输入。顺序反了会重做。
3. 求职场景下，"服务过 5 个真实用户并有原始反馈"比"做了个网站但没人用"可信度高。

**代价**：短期内没有可演示的界面；竞品拆解（原阶段 0.5）被推后——因为人力版跑通前，拆竞品只能拆到功能表面。

**什么情况会推翻这个决定**：如果 3 个案例都不需要人工介入就能跑（说明流程足够稳定），那可以直接跳到做工具。但按现在的提示词，大概率不会。

## D-006 · 2026-11-02 · 5 份样本实测后：加「三分类」，定位可能要从"改简历"偏到"投递决策"

**背景**：用 5 份虚构简历+JD 跑 v0.1，埋点召回 5/5，但同时发现：**5 份里只有 1 份（样本 4）是真正"改写就能提升"的**。另外 4 份里，3 份是能力缺口（改简历救不了），1 份需要先追问再重构。

**发现的问题**

| # | 问题 | 后果 |
|---|---|---|
| 1 | 事实库门槛 ≥20 条，真实简历只能拆出 6–10 条 | 5 份全部会被判"信息太少"，工具直接罢工 |
| 2 | 没有"可救性判断"，一律给改写建议 | 会给 SQL 零基础的人改简历去投数据分析师，等于推他进坑 |
| 3 | 重构型（B 类）直接给改写 | 会把"配合完成"改成"主导完成"，逼用户编造，面试必崩 |
| 4 | 缺"可迁移项"和"时间账" | 输出变成判决书，不给下一步 |

**定了**：出 v0.2，进四段之前先做三分类（A 措辞型 / B 重构型 / C 资格型），C 类禁止逐句改写，只给"缺什么零件 + 多久补 + 现在能投什么"。

**待定（更重要的一个判断）**：如果真实求职者里也是 4/5 属于资格不匹配，那这个产品的核心价值就不是"改简历"，是**"告诉你现在该投什么、该补什么"**。定位要从「简历优化助手」往「投递决策助手」偏。

**为什么现在不改定位**：样本是虚构的，比例未必代表真实人群。等 3 个真实案例跑完再看。**如果 C 类占比 >50%，PRD §1（用户）和 §2（问题）必须重写。**

**顺带记一个方法论问题**：这轮是开卷（样本附了埋点表），只能验证结构与逻辑覆盖，不能证明产品有用。**下一轮必须盲测**——拿没标答案的简历，让人自己判断"这条我原来没想到"。
