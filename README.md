# 简历诊断

**大多数简历工具在帮你改措辞。这个东西先告诉你：这个岗，你现在该不该投。**

投得了，它给出带事实编号的逐句改写；投不了，它一句都不改，只告诉你缺哪几件东西、补最短要多久、现在该投什么。

> 网页版是真能跑的：右上角填自己的模型 Key（默认 DeepSeek），贴简历 → 拆事实 → 贴 JD → 拿报告。

## 为什么不是"再做一个改简历的"

因为改措辞只对一类人有效：能力都有、只是没写清的人。

对另外两类人，改措辞会害人——给一个能力不够的人润色简历，等于推他进面试然后被挂。

拿 5 份样本跑第一版提示词时，这个问题暴露得很直接：

> 5 份里有 4 份，工具给了它们不该拿的改写建议。
> 其中 3 份根本没有岗位要的核心能力，工具还在帮它们润色"配合完成 20 场活动"。

所以现在第二步才是改，第一步是判。

## 30 秒看懂它怎么分

| 类型 | 判据 | 它给你什么 |
|---|---|---|
| **A 措辞型** | 核心要求都有证据，只是没写清 | 完整四段 + 逐句改写，每句挂编号 |
| **B 重构型** | 经历够，但全篇把自己写成了执行者 | 先追问"哪件是你自己决定的"，问到原料才改 |
| **C 资格型** | 核心要求里 ≥2 条完全无证据 | 不逐句改。只给可迁移项 + 时间账 + 先投什么岗 |

判断依据不是技能栏写了什么，是项目里有没有对应的动作。**技能栏是自我介绍，不是证据。**

## 它强制了什么

提示词里写"禁止编造"没有用——那只是请求，模型可以不听，而且你没法验证它听没听。

所以这里改成结构 + 脚本：

1. 简历先拆成带编号的事实条目（`f-001` 起）
2. 每一句结论和改写后面必须挂编号
3. 交付前跑校验器，抓两种错

```bash
$ python skill/scripts/verify_citations.py --report 报告.md --ledger ledger.json

[UNKNOWN_CITATION] 第 5 行 [f-099]
  用了事实库里不存在的编号 → 说明编了，删掉或补库

[VERB_UPGRADE] 第 4 行 出现「主导」，引用 f-018 原文是「协助」
  → 改回原动词

FAIL  修完再交付。
```

第二种是重点。任何工具都能说"我不编"，只有写了校验器才抓得住。**能被验证的约束才算约束。**

## 五种用法

**一、直接打开网页用**（什么都不用装）

打开 [ab900879.github.io/resume-diagnose](https://ab900879.github.io/resume-diagnose/)，右上角齿轮填一个模型 Key，然后按三步走。
默认接 DeepSeek（便宜、允许浏览器直连），换其他兼容 OpenAI 格式的接口也可以，但对方必须允许跨域。

事实库存在浏览器本地，换设备要重新建。

简历和 JD 都能直接传文件：`docx` / `pdf` / `txt` / `图片`（截图走本地 OCR，中文模型 1.7MB，识别在你的浏览器里跑）。全部解析都在前端完成，**文件不上传**。docx 解析是自己拆 zip 实现的，没有引第三方库。

**二、当作 WorkBuddy 技能**（体验最完整）

```bash
cp -r skill ~/.workbuddy/skills/resume-diagnose
```

之后直接说"帮我诊断这份简历，投 XX 岗"，它会自动读事实库、分类、按模板输出、跑校验。

**三、粘贴到任意大模型**（不需要任何工具）

用 [`prompt.md`](prompt.md)，两段分开跑，顺序不能反。ChatGPT / Claude / 豆包都能用。
缺点是校验器跑不了，你得自己盯着编号。

**四、命令行跑一遍，一次出四份**（不需要 Key）

```bash
node tools/agent.mjs --cv 简历.txt [--jd 岗位JD.txt] --out 输出目录
```

走 WorkBuddy 云服务的免密钥模型，三段连着跑：拆事实 → 诊断 → **生成改好的简历全文**。

**默认是类适配模式**：不给 `--jd` 也行——它按[类岗位需求库](references/jd-class-aipm.md)
（6 份在招 JD 提炼的"AI 产品实习这一类都要什么"）评估和改写。没人会为每一家单独改简历，
你拿一份简历投一类岗位，改出来就是适配这一类的。

产物四份，缺一份不算完成：

| 文件 | 是什么 |
|---|---|
| `01-诊断报告-<日期>.md` | HR 视角（每份简历只看 10 秒）+ 固定一段「投了没回音 ≠ 简历有问题」的判定边界 |
| `02-改好的简历-<日期>.md` | **纯净版，复制即可投**——零「依据」零说明文字 |
| `03-改动说明-<日期>.md` | 每处改动的原因和出处，跟简历分开 |
| `04-事实库-<日期>.json` | 下次改简历直接复用，不重拆 |

全程约 60 秒。

**五、只要校验器**

如果你已经在别处生成报告，直接把报告丢给 `verify_citations.py`，它不关心报告是谁写的。

| 项 | 数 |

四个硬伤和改法都在 [`docs/eval-report-v1.md`](docs/eval-report-v1.md)。方法本身的漏洞也写在第一段：样本带答案，等于开卷考试，只能验证结构稳不稳，不能证明对真实用户有用。

## 边界

- **没有真实用户。** 只有作者本人和一份虚构样本集。这是最该补的一块，也是下一轮要做的：拿 3 份同学的真实简历盲测，统计 C 类占比。
- **C 类占比可能推翻定位。** 如果真实人群里 C 类超过一半，这个产品的核心就不是"改简历"，是"告诉他该投什么"。判定线写在 `docs/DECISIONS.md` D-006。
- **事实库含隐私，不进仓库。** 逻辑公开，数据私有。
